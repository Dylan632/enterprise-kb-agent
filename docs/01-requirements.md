# 01 · 需求

## 1. 用户

**主要用户**：企业普通员工（非 HR / 财务专业），在需要确认制度细节时使用。
**次要用户**：HR / 财务 / 行政的制度维护者，关心"答错了会不会被追责"。

## 2. 要解决的问题

企业制度文档分散在多个文件里，员工的实际困难不是"搜不到文件"，而是三件事：

1. **不知道哪个说法算数** —— 同一件事在两份文件里写了不同数字。
2. **不知道答案有没有依据** —— 问同事、问通用大模型，得到的答案无法追溯。
3. **不知道自己问的有没有覆盖** —— 制度没写的内容，容易被一本正经地编出来。

所以本项目的目标不是"做一个 RAG 问答"，而是**做一个敢说"我不知道"和"这里自相矛盾"的问答**。

## 3. 目标（可度量）

| 编号 | 目标 | 度量方式 | 目标值 |
| --- | --- | --- | --- |
| G1 | 有依据地回答 | 每条 `answered` 至少 1 条通过逐字校验的引用 | 100% |
| G2 | 不编造 | 资料外问题返回 `insufficient`，引用为空 | 100% |
| G3 | 不擅自裁决冲突 | 不可判定冲突返回 `need_confirmation` | 100% |
| G4 | 可判定冲突给出依据 | 答案中说明替代关系/生效日期 | 100% |
| G5 | 决策可回溯 | 每步含 参数 / 返回摘要 / 后续动作 / 依据 | 100% |
| G6 | 上限可控 | 达到步数上限返回 `unfinished` | 100% |

## 4. 范围

**做**

- 单轮问答 + 轻量上下文追问（指代消解）
- 词面检索（BM25）+ 版本感知加权
- 查询改写（由模型决定，非固定重试）
- 跨文档冲突检测，区分可判定 / 不可判定
- 引用逐字校验与系统侧兜底降级
- 结构化 Trace（JSON + Markdown）
- 工具故障注入与失败降级

**不做**（题面允许，且 3 小时预算内不划算）

- 文档上传、解析、切分流水线（改用预置合成语料）
- 向量检索 / 混合检索（BM25 足够，且零依赖更利于评审复现）
- 文档级权限、多租户
- Web 界面、线上部署
- 多 Agent 协作

## 5. 验收点矩阵

| 题面验收点 | 用例 | 期望状态 | 关键断言 |
| --- | --- | --- | --- |
| 明确答案 | Q1 | `answered` | 引用 D01#3，答案含 500 元/晚 |
| 文档冲突 | Q2 | `need_confirmation` | 同时引用 D01、D02，并列 30 / 15 |
| 资料外问题 | Q3 | `insufficient` | 引用为空，说明缺什么 |
| 改写后的相似问题 | Q4 | `answered` | Trace 中出现 ≥2 次不同 query 的检索 |
| 上下文追问 | Q6 | `answered` | 检索词继承上一轮"年假" |
| 工具失败 | Q7 | `error` | read_chunk 全失败后停止，不凭片段作答 |
| （额外）版本冲突 | Q5 | `answered` | 只引用 D03，答案含"依据" |
