## 3. 我的实际投入

### 3.1 提供问题与素材

- 提供考核页面截图（试卷说明、考核规则、Agent 决策要求、交付规范、四道项目题）。
- 提供我此前的两个项目源码：`PaiCLI`（Java CLI Agent，ReAct + 工具注册 + 预算 + Trace）、`PaiSmart`（Spring Boot 企业 RAG，ES 混合检索 + 引用编号映射）。
- 提出"把两个项目合并做企业知识问答"的初始设想。

### 3.2 做出（或确认）的三个判断

1. **选题**：四道题中选定第 3 题（企业知识问答）。理由是与既有经验重合度最高，且题面的高分依据落在冲突处理而非检索本身。
2. **否决"合并两个仓库"**：AI 分析后指出 PaiSmart 需要 MySQL + ES + Kafka + MinIO + Redis 才能跑、PaiCLI 有 200 余个与本题无关的文件，直接合并会导致"评审跑不起来"且"个人贡献无法界定"。我接受了这个判断，改为"借鉴设计、重写实现"。
3. **语料冲突设计**：两组冲突的语义不同——D01/D02 是"并行执行、无优先级"的**不可判定**冲突，D03/D04 是"新版替代旧版"的**可判定**冲突。这个区分决定了 Agent 要有两种不同的正确行为，是我确认的设计前提。

### 3.3 提供运行条件

- 提供 DeepSeek API key，使 live 模式得以实测（`examples/` 中的 7 组 trace 由真实模型产出）。
- key 仅通过环境变量传入，未写入任何文件；仓库内已加 `tests/test_no_secrets.py` 做泄漏自检。

### 3.4 委托外部模型做了三轮独立评审与人工走查

交付前我把项目打包（`enterprise-kb-agent-review/`）先后交给独立模型做审查。
第一轮报出"模型不调工具直接作答会绕过全部校验"等 5 个问题；第二轮进一步发现"问住宿报销标准被误判为报销期限冲突""未调用 `read_chunk` 仅凭检索 `snippet` 也能通过引用校验""文档描述仍停留在离线模拟器步骤"等 5 项深层问题；第三轮又排查出"同轮并发提前提交"与"新旧数字混搭放行" 2 项边界问题。12 条已全部修复，并补齐了 21 条回归测试与动态替换文档内容测试。

这件事说明：**"34 个测试全过"和"没有漏洞"是两件事。** 测试是我按自己的假设写的，
假设本身错了，测试就测不出来。

## 5. 开发中的两次关键取舍（记录过程，不冒领功劳）

这两处是方案层面的分歧，记录下来是因为它们影响了最终形态：

**① 冲突检测做成独立工具，而不是检索后自动触发。**
自动触发更省事，但 Trace 里就看不到"模型决定去查冲突"这个动作。改成工具后，
`examples/02-doc-conflict/trace.md` 的第 3 步才成为一条可核对的证据。
题面要的是可观察的决策链，不是"结果对了就行"。

**② 不用 jieba 分词。**
多一个依赖就多一个评审安装失败的可能，而制度文本用汉字二元组已经够用。
这个取舍写进了 `docs/02-solution.md` 的技术取舍表。

## 6. 未验证的部分

- **未做语义级蕴含校验（NLI）**：当前 `verify.py` 校验引文逐字存在性与数值一致性，若数值一致但语义相反需引入独立核验模型。
- **未测大规模语料**：只用 10 篇 / 29 片段，数百篇文档下的召回质量未验证。
- **未做成本与并发评估**：单进程 CLI，7 组用例约 40 次模型调用，未统计 token 成本。
- **未验证其他模型**：只测了 `deepseek-flash`，换模型后提示词约束是否仍生效未知。
