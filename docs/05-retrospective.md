# 05 · 复盘

## 1. 最难的一个问题

**不是让 Agent 答对，而是让它在答不对的时候敢停下来。**

最初的版本里，"检索不到"的处理是：拿 top1 的片段，让模型基于它作答。
在 Q3（年会预算）上，检索确实返回了 3 条命中——都含"公司"两个字，coverage 0.111。
如果不看 coverage，只看"有没有结果"，这个查询会走进一条看起来很正常的路径：
读片段 → 片段里没有预算 → 模型开始用常识补。

真正解决问题的动作是把"相关度"从隐含状态变成显式信号：

```python
# index.py
def classify(coverage: float) -> str:
    if coverage >= 0.34: return "strong"
    if coverage >= 0.12: return "weak"
    return "none"
```

`hit_quality=none` 一旦出现在工具返回值里，"这次没搜到"就成了模型必须处理的一个观察结果，
而不是它自己心里的猜测。**拒答不是靠提示词求来的，是靠工具如实汇报换来的。**

这件事让我改变了对"工具设计"的理解：工具不该只返回数据，还该返回它对这批数据的置信度。

## 2. 第二个难题：旧版本为什么总排在前面

Q5 一开始稳定引用 D04（5 天）而不是 D03（7 天）。查下来是 BM25 的长度归一化：
D04#1 有 54 字，D03#1 有 79 字，同样的词频下短文档得分更高。

第一反应是在提示词里加"注意文档版本"。写完就意识到这是错的——
这等于用模型注意力去弥补检索层的语义缺失，换个模型、换个问法就会退化。

正确做法是把版本语义放回检索层：

```python
STATUS_WEIGHT = {"active": 1.0, "draft": 0.8, "archived": 0.55}
score *= STATUS_WEIGHT.get(doc.status, 1.0)
```

并且旧版**不能直接过滤掉**——它在冲突举证时仍然需要被读到（Q5 第 4 步）。
所以是降权而不是排除。这个区分（"不该排在前面" ≠ "不该出现"）是这次最具体的一个收获。

## 3. 关于"合并两个既有项目"的判断

我最初的想法是把 PaiSmart（企业 RAG）和 PaiCLI（CLI Agent）合并起来直接交。
放弃这个方案后，反而想清楚了一件事：

**考核看的不是"我有什么"，而是"我在约束下做了什么选择"。**

- PaiSmart 的 ES + Kafka + MinIO 五件套，在企业里是加分项；在"评审要一条命令跑起来"的约束下是负债。
- PaiCLI 的 208 个文件里，browser / LSP / MCP / TUI 与本题无关，带着它们只会让"哪部分是我写的"变得无法回答。

最后落到的规模是约 1900 行（含注释与文档字符串，不含测试），每一行都能解释为什么在这。
`docs/02-solution.md` 第 7 节专门写了"借鉴了什么、没搬什么"，我认为这比多写 5000 行更有说服力。

## 4. 学习收获

1. **可观察性优先于聪明。** 把 `check_conflicts` 做成独立工具而不是内置步骤，Trace 里才留下"模型决定去查冲突"这条证据。凡是不能出现在 trace 里的能力，评审就无法确认它存在。
2. **机械可校验的事不要交给概率。** 引用是否逐字来自原文，是一个字符串包含问题，不该让模型"注意不要编造"。`verify.py` 用 30 行代码把这类风险关掉了。
3. **提示词不该用来补架构的洞。** 版本排序、相关度判断这两个问题，都能用提示词"糊"过去，但都会在换模型时退化。判断标准很简单：这个问题的正确答案是否与模型无关？如果是，就不该写在提示词里。
4. **拒答需要设计出口。** `insufficient` / `need_confirmation` / `unfinished` / `error` 四个状态不是错误码，是四种不同的"正确行为"。没有它们，模型只有"答"和"崩"两个选项。

## 6. live 结果推翻了我的两个判断

跑真实模型之前，我基于离线结果有两个判断，实测后都被修正：

**① "改写查询是串行的"**
离线模拟器的路径是：搜一次 → 没命中 → 改写 → 再搜。我据此以为这是正常节奏。
真实模型首轮就并发发了两条不同措辞的 query（`出差住宿标准 一线城市` 与
`差旅费用报销 住宿费限额`），用更少的轮次拿到更高的覆盖率。
**我的模拟器把"思考"实现成了"逐条试错"，这本身就是一种能力缺失。**

**② "引用越少越干净"**
我把 Q5 的断言写成"禁止引用 D04"，因为直觉上引用旧版就是错的。
真实模型引用了 D03#1（7 天）+ D04#2（版本说明）——后者正是"旧版已废止"这句话的依据。
引用不是越少越好，而是**每条引用都要能支撑答案里的某一句**。

这两个修正让我意识到：离线模拟器能验证"链路通不通"，但会悄悄把"我以为的合理行为"
固化成"正确行为"。**用 Mock 做验收，最大的风险不是 Mock 不准，是我把 Mock 当成了标准答案。**

## 7. 关于密钥的一次提醒

提交前我意识到一个问题：跑 live 模式要带 API key，那 key 会不会跟着仓库一起交上去？

实际检查下来没有（`grep` 全仓库无 `sk-` 字面量，key 只走了环境变量），
但这件事暴露了一个更普遍的问题：**"我没写进代码"和"它没泄漏"是两件事。**
于是补了三道防线——`.gitignore` 扩展规则、`.env.example` 留空、
`tests/test_no_secrets.py` 在每次 `pytest` 时扫描全仓库。

更根本的一点：key 一旦出现在聊天记录、截图或公开仓库里，就应该吊销重发。
环境变量只保证"不落盘"，不保证"没外泄过"。

## 8. 一句话总结

这次做的不是一个"能回答制度问题"的 Agent，而是一个**在证据不足时会把话说清楚的 Agent**。
前者的天花板是模型能力，后者的天花板是工程设计——而这道题考的是后者。
